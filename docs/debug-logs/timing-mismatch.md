# 디버그 기록 2 — 타이밍이 채보와 어긋나는 곡

## 증상

- 곡은 불러와지고 앞부분은 맞는데, 어느 지점부터 노트가 채보보다 일찍·늦게 떨어집니다("채보대로 쳤는데 계속 죽는다").
- 한 지점부터 **같은 양만큼** 계속 밀리면 거의 항상 그 지점의 floor 하나(또는 몇 개)의 시간을 잘못 센 것입니다.
- 게임 링크가 있으면 `link tiles`가 가장 빠릅니다: 한 타일만 차이가 튀면 그 타일이 원인입니다.

## 진단 순서

1. **지점을 floor로 바꿉니다.** 콘솔 `note`가 노트 번호·시각·타일을 보여 줍니다. hit n의 floor는 floor 1부터 센 n번째 중간 회전(999)이 아닌 floor이고, floor n의 시간은 floor n−1 회전의 결과라 원인은 대개 그 floor와 바로 앞 floor입니다.
2. **그 floor 앞뒤 이벤트를 JSON 그대로 봅니다**(속성 전체 — 원인이 속성 하나일 수 있음).

   ```bash
   PYTHONIOENCODING=utf-8 python - <<'EOF'
   import json
   d = json.load(open(r'.local\tmp\<이름>\<id>\main.adofai', encoding='utf-8-sig'))
   angles = d.get('angleData')          # pathData 맵이면 따로 풀어야 함
   for a in d['actions']:
       if 500 <= a['floor'] <= 560 and a['eventType'] in ('SetSpeed', 'Twirl', 'Pause', 'Hold', 'FreeRoam', 'Checkpoint', 'AutoPlayTiles', 'MultiPlanet'):
           print(json.dumps(a, ensure_ascii=False))
   print(angles[500:560])
   EOF
   ```

3. **사본으로 한 곡 대조**([README](README.md)). 파서와 기준 계산기가 **다르면** 어느 쪽이 게임과 다른지 IL로 가립니다(`worst floor`가 원인). **같으면** 두 구현이 같이 모르는 규칙이 있다는 뜻이니 파서가 읽지 않는 속성을 게임이 어떻게 읽는지 확인합니다.
4. **IL로 규칙을 확정**하고 확인된 만큼만 구현합니다.
5. **파서와 기준 계산기에 따로 넣습니다**(계산기는 파서를 부르지 않음). 고치기 전 코드에서 실패하는 테스트, 사본 재대조, `CurrentVersion` 올리기.
6. **같은 패턴의 다른 곡**을 앱 저장소 `maps/` 사본(읽기만)에서 찾아 사용자에게 알립니다.

## 주의

### 2026-10-13 · inspect 첫 타일 놓침 — 시작 대기 중 노트 소비와 사전 입력

사용자는 시작 전 입력 버퍼로 첫 타일이 늘 놓침 처리된다고 제보했습니다. 코드에서는 게임 시계가 움직이기 전 판정선의 첫 노트를 이미 지난 것으로 소비하고, 첫 계획의 25ms 안 노트까지 건너뛰는 경로가 확인되었습니다. 움직이는 시계에서만 계획하고 이미 지난 노트만 건너뛰도록 수정했습니다(첫 타일 회귀 테스트는 수정 전 실패). 카운트다운에 설정의 8개 레인 키·Space·Enter 사전 입력도 추가하되 첫 노트 40ms 전 마감, 종료·일시정지 시 취소합니다. 실제 게임의 버퍼 원인과 사전 입력의 효과는 확인 대기이며 이번 검증은 가짜 시계·키 전송기로 수행합니다.


### 2026-10-13 · inspect 중단 후 재시작 — 이전 위치·완료 노트·일시정지 상태 유지

새 inspect가 이전 곡 끝 시각의 노트를 건너뛰는 것만으로 종료되고, 게임이 되감겨도 완료 노트가 남으며, Esc 뒤 앱 일시정지가 남으면 follower가 HeldHere에 묶이는 앱 경로를 회귀 테스트로 재현했습니다(수정 전 세 항목 실패). 새 측정의 조기 종료를 막고, 60ms 넘는 되감기는 기존 키·예약·완료 노트를 복구하며, 시작 때 로컬 일시정지를 해제합니다. 작은 시계 보정은 노트를 반복하지 않습니다. 체크포인트 앞의 숨긴 노트는 제외하고 사전 입력도 다음 표시 노트 전에 마칩니다. 실제 게임의 FailMiss 개선은 확인 대기이며, 열린 메모의 곡 중간 놓침 13건 전체를 해결한 것으로 표시하지 않습니다.

### 2026-10-13 · Miku inspect 메모 — 사전 입력 예약 누락·채터링 필터 조사 (1.0.8)

**확인·수정한 앱 결함**: 콘솔이 앞에 있는 동안 사전 입력 예약을 꺼내 버려 실제 게임으로 전환한 뒤 아무 키도 예열하지 않는 경로를 가짜 전송기로 재현했습니다(수정 전 실패). 게임이 앞으로 올 때까지 예약을 유지하고, 늦어진 예약도 실제 전송 사이 40ms 간격을 유지하며, 첫 노트 100ms 전까지 모두 떼도록 수정했습니다. 측정 도중 게임 판정이 초기화되면 시작 개수를 빼서 음수로 나오던 집계도 재현(수정 전 실패)하고 양의 증가 누적으로 수정했습니다. 초기화 직후 0 표본이 생략되고 첫 읽기에 이미 판정이 있으면 이를 버리지 않고 새 회차의 0을 기준으로 포함합니다(이 경로도 수정 전 실패 확인). 1.0.6·1.0.7의 시작·되감기 수정과 함께 검증했습니다.

**원본 노트 확인**: 해당 v25 캐시의 hit 1450개 중 HoldEnd 65개를 제외하면 입력 대상은 1385개입니다. 옛 결과의 1384개·첫 타일의 마지막 입력 없음은 첫 노트 누락과 일치합니다. 캐시를 프로젝트 내부에 복사해 최대 타일 수만 4로 맞춘 진단에서는 과거에 적힌 마지막 입력 레인 9개 중 3개만 같았습니다. 나머지 당시 설정은 메모에 없으므로 현재 배치를 과거 배치로 간주하지 않습니다. 파서·맵 hit 시각·레인 규칙은 바꾸지 않았습니다.
