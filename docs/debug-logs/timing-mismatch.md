# 디버그 기록 2 — 타이밍이 채보와 어긋나는 곡

## 증상

- 곡은 불러와지고 앞부분은 맞는데, 어느 지점부터 노트가 채보보다 일찍·늦게 떨어집니다("채보대로 쳤는데 계속 죽는다").
- 한 지점부터 **같은 양만큼** 계속 밀리면 거의 항상 그 지점의 floor 하나(또는 몇 개)의 시간을 잘못 센 것입니다.
- 게임 링크가 있으면 `link tiles`가 가장 빠릅니다: 한 타일만 차이가 튀면 그 타일이 원인입니다.

## 진단 순서

1. **지점을 floor로 바꿉니다.** 콘솔 `note`가 노트 번호·시각·타일을 보여 줍니다. hit n의 floor는 floor 1부터 센 n번째 중간 회전(999)이 아닌 floor이고, floor n의 시간은 floor n−1 회전의 결과라 원인은 대개 그 floor와 바로 앞 floor입니다.
2. **그 floor 앞뒤 이벤트를 JSON 그대로 봅니다**(속성 전체 — 원인이 속성 하나일 수 있음).

   ```bash
   PYTHONIOENCODING=utf-8 python - <<'EOF'
   import json
   d = json.load(open(r'.local\tmp\<이름>\<id>\main.adofai', encoding='utf-8-sig'))
   angles = d.get('angleData')          # pathData 맵이면 따로 풀어야 함
   for a in d['actions']:
       if 500 <= a['floor'] <= 560 and a['eventType'] in ('SetSpeed', 'Twirl', 'Pause', 'Hold', 'FreeRoam', 'Checkpoint', 'AutoPlayTiles', 'MultiPlanet'):
           print(json.dumps(a, ensure_ascii=False))
   print(angles[500:560])
   EOF
   ```

3. **사본으로 한 곡 대조**([README](README.md)). 파서와 기준 계산기가 **다르면** 어느 쪽이 게임과 다른지 IL로 가립니다(`worst floor`가 원인). **같으면** 두 구현이 같이 모르는 규칙이 있다는 뜻이니 파서가 읽지 않는 속성을 게임이 어떻게 읽는지 확인합니다.
4. **IL로 규칙을 확정**하고 확인된 만큼만 구현합니다.
5. **파서와 기준 계산기에 따로 넣습니다**(계산기는 파서를 부르지 않음). 고치기 전 코드에서 실패하는 테스트, 사본 재대조, `CurrentVersion` 올리기.
6. **같은 패턴의 다른 곡**을 앱 저장소 `maps/` 사본(읽기만)에서 찾아 사용자에게 알립니다.

## 주의

기준 계산기(`GameRuleTimingComparison.cs`)는 별도 구현이지만 같은 IL을 읽어 **같은 누락을 공유할 수 있습니다**. 대조 통과는 게임과 일치한다는 뜻이 아니며, 게임과의 일치는 `link tiles`나 사용자의 플레이로만 확인됩니다. 보고할 때 셋을 구분합니다.
- **2026-10-12 · cosMo@暴走P - THE END OF HATSUNE MIKU (3011005213)** — "공이 많아지는 기믹(3행성)부터 안 맞음". **해결**: 게임을 이 곡에 둔 채 링커 파이프를 읽기 전용으로 열어 게임 자체 타일 시각(1561 floor)을 받아 대조 — floor 310부터 3행성 구간마다 게임 쪽 회전이 정확히 60° 짧았음(180°→120°, 90°→30°, 270°→210°, 시계·반시계 모두, 미드스핀 다음은 그대로). 파서가 IL의 진입각 이동을 "길어짐"으로 잘못 읽고 있었음 → 부호를 바꿔 파서 `adofai-v25-three-planets-shorter`. 고친 뒤 hit 1450개 모두 게임과 오프셋 3000ms(카운트다운)로 같음(1ms 안). 기준 계산기에도 IL 그대로 넣어 최대 0.002ms. Workshop에서 3행성을 쓰는 맵은 이 곡뿐.

### 2026-10-12 · THE END OF HATSUNE MIKU (3011005213) — 수정 전 캐시로 재생

사용자 재제보: 수동 시작으로 재생할 때 3행성 전환부터 일치하지 않음. 게임 128번 타일 제보는 사용자 실수로 정정(정상). 미처리 메모 없음.

앱 저장소의 해당 곡 `ParserVersion`은 `adofai-v24-pause-correction`, 현재 소스와 Debug·Release DLL은 `adofai-v25-three-planets-shorter`. 이전 캐시와 현재 파서의 첫 hit 기준 시각을 대조하면 128·310번 타일은 같지만, **311번부터 133.333ms 늦어지고 325번에서 1626.667ms 늦음**. 수정 전 3행성 계산이 캐시에 남아 있었음. 현재 파서에 추가 계산 변경은 필요하지 않음.

사용자가 한 곡의 독립 대조를 명시적으로 승인한 뒤 앱 저장소 맵의 임시 사본만 검사: hit 1450개, 독립 계산 최대 차이 0.001784ms(간격 0.000154ms, 재시작 구간 0.002071ms), Debug 일반 테스트 267/267·한 곡 대조 포함 268/268, 경고·오류 0. 원본 SHA-256 `30316147…B83EA`·수정 시각 불변. 이번 검사는 독립 계산 대조이며 새 게임 실측은 하지 않음.

**적용**: 앱 재시작 → Map Sync(콘솔 `sync`도 같은 경로) → 곡 다시 불러오기. Load Song·Reset만으로는 이전 캐시를 재파싱하지 않음. 앱 저장소 캐시·설정은 에이전트가 직접 수정하지 않음.
