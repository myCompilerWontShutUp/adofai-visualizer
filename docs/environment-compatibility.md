# 일반판 외부 환경 대응

조사·검증일: 2026-09-13 KST. 대상은 Windows 일반판의 커스텀 맵과 수동 연습 Visualizer입니다. DLC 기능은 구현하지 않았습니다. 아래의 지원은 모든 일반판 이벤트나 모든 게임 버전의 지원을 뜻하지 않습니다.

## 확인한 근거

- [개발사의 Steam 공지](https://steamcommunity.com/app/977950/allnews/)에는 v3.1 계열의 보정 화면·중간 시작 동기화 수정·에디터 일시정지, v3.3.1의 선택적 Color Track 속성·일시정지 관련 수정이 기록되어 있습니다. DSP 버퍼 변경 뒤 재보정이 필요할 수 있다는 안내와, 키 제한 기능도 확인했습니다. 게임 앱 버전만으로 맵 형식이나 입력·화면 지연을 동일하다고 볼 수 없습니다. 공지는 변경 내역 근거이며 타이밍 수식의 근거로 사용하지 않았습니다.
- 설치된 게임의 `scrConductor.get_adjustedCountdownTicks`, `get_dspTimeSongPosZero`, `get_calibration_i`, `get_calibration_v`, `Update`를 **ReflectionOnly 파일 읽기**로 확인했습니다. 카운트다운 틱/속도, 곡 오프셋, 오디오 pitch, 입력·화면 보정은 별도 값입니다. 게임 프로세스 메모리는 읽거나 수정하지 않았습니다. 실제 메서드 실행·주입도 하지 않았습니다.
- 확인 파일: `C:\Program Files (x86)\Steam\steamapps\common\A Dance of Fire and Ice\A Dance of Fire and Ice_Data\Managed\Assembly-CSharp.dll`, SHA-256 `0D1524DABF0F8C67AA58BA1992D6ED858522B9094490EBBB00E5E8AEFF7F40CD`. 이 파일 확인은 다른 빌드와의 동작 동일성을 보장하지 않습니다.
- [Unity AudioSource.pitch 문서](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSource-pitch.html)와 위 게임 파일의 pitch 사용을 참고했습니다. 우리 배속은 수동 시간 비례 변환이며 게임 오디오 엔진·특수 보정을 복제하지 않습니다.
- 기존 각도·Pause 타이밍 근거는 [파서 문서](adofai-parser.md) 및 [수치 대조 문서](timing-comparison.md)를 유지합니다. 공개 구현 [SharpFAI 계산기](https://github.com/adofaiex/SharpFAI/blob/main/SharpFAI/Util/FloorTimingCalculator.cs)는 기존 계산의 보조 근거이며 패키지·쓰기 기능을 도입하지 않았습니다.

## 시간 처리

`r = 배속 / 100`, `D = 시작 대기 시간(ms)`로 둡니다. 체크포인트 첫 hit를 뺀 원본 시각을 `r`로 나눈 뒤 동타·동적 모드를 계산합니다. 동타 처리 후 모든 표시 hit에 `D`를 더합니다. 따라서 동타 10ms와 모드 경계는 **실제로 표시·재생되는 시간 간격** 기준이고, 시작 대기 시간은 묶음에 영향을 주지 않습니다. 파서·캐시에는 이 값을 저장하지 않습니다.

체크포인트 진행은 `원본 시작 시각 + max(0, 경과 시간 - D) × r`로 환산합니다. 표시 보정은 레인 렌더링에만 적용합니다. 일시정지에서는 경과 시간을 고정하고, 이어하기에서 시계 기준점만 조정합니다. 기본값 100%·0ms는 기존 동작입니다.

예: 원본 상대 시각 `0, 500, 4000ms`, 배속 50%, 시작 대기 1500ms이면 표시 시각은 `1500, 2500, 9500ms`입니다. Start 직후 첫 노트까지 1.5초이며, 중간의 긴 간격도 그대로 두 배가 됩니다.

## 직접 확인할 순서

1. 최신 Release 실행 후 맵 동기화를 한 번 실행하면 형식 버전·시작 메타데이터 안내가 캐시에 반영됩니다. 새 수동 대기·배속·일시정지 기능 자체는 기존 타임라인 캐시로도 사용할 수 있습니다.
2. 처음에는 배속 100%, 시작 대기 0ms로 두고 게임의 첫 실제 타격 때 시작합니다. 메뉴 확인·로딩 중에는 시작하지 않습니다.
3. 게임 시작 버튼과 함께 Visualizer를 시작하고 싶다면 그 입력부터 첫 실제 타격까지의 시간을 측정해 시작 대기 값으로 입력합니다. 카운트다운 숫자만으로 자동 계산하지 않습니다. 반복 확인 후 맞춥니다.
4. 게임에서 배속을 바꾸면 Visualizer 배속도 같은 값으로 바꾸고 Reset합니다. 배속이 바뀌면 동타·동적 키 수 결과도 달라질 수 있습니다. 3노트 이상 묶음은 2동타와 단타로 나눠 표시합니다([동타 규칙](note-rules.md)).
5. 게임을 멈췄다면 Visualizer도 일시정지합니다. 별도로 조작하는 만큼 재개 오차가 생겼다면 체크포인트를 다시 선택해 첫 타격 기준으로 맞춥니다. 자동 게임 상태 감지나 동기화는 없습니다.

## 게임과 함께 실행할 때 렉 (GPU 배치)

2026-09-15 사용자 제보: Visualizer만 실행하면 부드럽지만, ADOFAI에서 연출이 무거운 곡(AnythingBecomeMoe - ヤラララ)을 함께 재생하면 Visualizer가 심하게 끊겼습니다. 작업 관리자에서는 두 프로그램 모두 가벼워 보였습니다.

- **원인(측정):** 노트북 하이브리드 GPU(내장 Intel Arc 130T가 화면과 dwm 합성 담당, RTX 4050 6GB)에서 Visualizer가 게임과 같은 RTX 4050에서 렌더링되고 있었습니다. 그 GPU의 3D 사용률은 게임만으로 79~90%였고, Visualizer의 화면 갱신은 게임 프레임 뒤에서 기다린 뒤 내장 GPU로 복사되었습니다. Visualizer 자체는 GPU 3D 약 5%, GPU 메모리 27MB, CPU 0.5%였고, VRAM(6GB 중 3.1GB)은 부족하지 않았습니다. 측정은 프로세스 정보, Windows GPU 성능 카운터(어댑터 luid별 GPU Engine 사용률·메모리), 앱별 GPU 설정 레지스트리를 읽기만 했습니다.
- **해결(사용자 확인):** Windows 설정 → 시스템 → 디스플레이 → 그래픽 → 앱 추가에서 `src\Visualizer.App\bin\Release\net9.0-windows\Visualizer.App.exe`를 **절전(내장 GPU)**으로 지정하고 Visualizer를 다시 실행했더니 렉이 완전히 사라졌습니다. Debug 실행 파일은 경로가 달라 따로 지정해야 합니다.
- Visualizer는 게임의 GPU·프로세스·설정을 바꾸지 않으며, Windows 설정도 코드가 쓰지 않습니다. 비슷한 제보가 오면 코드 성능보다 먼저 두 프로그램이 같은 GPU를 쓰는지 확인합니다. 소프트웨어 렌더링 옵션은 이번에 필요하지 않아 구현하지 않았습니다.

## 검증 결과

`build.ps1 -Configuration Release -Test -ReadOnlyMapRoot 'C:\Program Files (x86)\Steam\steamapps\workshop\content\977950' -CompareGameRules`: 경고·오류 0, **60/60 그룹 통과**. 새 회귀는 `EnvironmentCompatibilityTests.cs`에 있습니다. 시작 대기, 배속과 동타 경계, 일시정지 중 대기 시간, 체크포인트 활성화, 형식 안내, 잘못된 메타데이터, 이전 캐시 안내, 한국어·영어 400×640 화면을 검증했습니다.

실제 맵 4곡의 SHA-256과 수정 시각은 불변입니다. HeHeHe는 기본 동타 10ms에서 명시적으로 중단하고 0ms에서 복구하는 기존 검증을 유지했습니다. 파서 타이밍과 독립 기준 계산의 최대 차이는 약 0.011603ms입니다. 실제 게임 오디오·입력과 수동 배속·대기 기능의 종단 간 동기화 측정은 별도로 남아 있습니다.
